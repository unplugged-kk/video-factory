# 09 / Frontend architecture recommendation

**Research date:** 2026-11-24. **Scope:** runtime choices and migration trigger. **Evidence / sources:** `contentos/ui/`, `contentos/dashboard.py`, `package.json`, prior `docs/ui-discovery/creator-studio/frontend-architecture-decision.md`, [component audit](12-REACTBITS-MOTIONSITES-AUDIT.md). **Verified:** current ES modules and same-origin API need no React production runtime; 25 existing UI unit tests passed. No bundles built or profiled.

| Criterion | A Vanilla ES modules | B Selective React island | C Full React |
|---|---|---|---|
| Change and regression scope | Lowest; keep shell and APIs; introduce cohesive feature folders | One mount/unmount and event bridge plus bundler/assets boundary | Highest; route, component, focus, state, fixtures and packaging all need parity |
| Runtime size / dependencies | No framework minimum; pay for owned code only | React + DOM plus component dependencies even if one tool; measure route-split cost | App-wide runtime and new dependency lifecycle; splitting helps not eliminates |
| Accessibility | Native controls and semantic headings; manual focus/list state | Native outer shell, island responsible for focus handoff and its own semantics | Mature tooling but no automatic accessibility; new keyboard regression surface |
| Testability and DX | Existing Node unit and Playwright; pure reducers/contract tests | Both harnesses or shared browser tests, mock bridge cleanup | Familiar component tooling; replacement tests/config need care |
| Maintenance / extension | Manage complexity with feature-owned state, no global mutable store | Good for independently bounded rich widget; two models to maintain | Consistent component ecosystem if state workflows justify rewrite |
| Local/server boundary | Existing static files and same-origin token | Build artifacts served locally, zero CDN, no duplicated token handling | Same Python API feasible, more asset version and local caching concerns |

**Recommendation:** choose A now and use standards/native components plus CSS motion. Organize routes as `screen + view model + API contract` and retain shared components for status, media, dialog and stable list updates. Server owns readiness and transitions. No two code paths for grant or export. Prototype a keyboard-first batch editor with 20 rows, stale mutations and mixed readiness. Only consider B for a demonstrably difficult isolated tool such as deep timeline editing; must lazy load, accept inputs and emit intents only, cleanly unmount, be offline, preserve accessibility and pass measured budget. Do not use a decorative React-dependent effect as the reason for B. Consider C only after two or more planned surfaces show repeatable state/maintenance issues not resolved by A and a rewrite can pass parity behind an opt-in route. Avoid React for the initial static prototype.

Acceptance to compare later: transfer and parse size on cold offline load, keyboard/magnification fixtures, deterministic reconnection, render CPU/memory contention, build packaging, and complexity measured in ownership boundaries and global state, not lines alone. No assumed React overhead numbers. **Assumptions:** maintainers can retain native controls and state contracts. **Open questions:** evidence threshold after the batch prototype and asset picker, governance for dependency exception.
