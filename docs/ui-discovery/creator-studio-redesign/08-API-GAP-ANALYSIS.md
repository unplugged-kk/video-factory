# 08 / API gaps and contracts

**Research date:** 2026-11-24. **Scope:** existing versus candidate server operations. **Evidence / sources:** `contentos/ui_api.py:dispatch`, `contentos/ui_api.py:write_authorized`, `contentos/ui/api.js`, `contentos/ui_state.py`, `contentos/dashboard.py`, `tests/test_ui_api.py`, [approval policy](../../audit/APPROVAL_POLICY.md). **Verified:** token and local Host/origin checks, spec collision, lock conflict, stale digest and bounded log/media have test coverage. Session token is not multi-user authentication.

| Operation | Current `/api/v1` routes | Gap / recommended implementation contract |
|---|---|---|
| Readiness and planning | `GET /health[?refresh=1]`, `/capabilities` | Proposed `POST /plans/validate` with `{intent,inputs,target,options}` → version, ordered capabilities, input issues and manual steps. No side effects, billable generation or readiness inferred from registry existence. |
| Author and execute | `GET /jobs`, `/jobs/:id`; `POST /specs/validate`, `/specs`, `/jobs/:id/run` | Preserve validate/create distinction. Proposed draft revisions with conditional compare; never rewrite an approved file. Keep `ALREADY_RUNNING` distinct from accepted new work. |
| Observe and recover | job `/events`, `/stages/:stage/log`, `GET/POST /rerun`, `POST /qa`, `GET/POST /queue`, `POST /queue/:id/requeue` | Reread after events, report actual queue transitions, bounded logs. No worker start, cancel or fleet management added. |
| Manual Track B | `POST /jobs/:id/track-b/:action` | Do not treat plan artifact as renderer approval. Expose only actions from detail; track manual ownership, errors and completed artifacts, not artificial % complete. |
| Review | `POST /jobs/:id/preview`, `/approve` `{gate, seenDigest,...}`; job detail + media | After PF-05/PF-02, proposed exact subject/revision/digest reference pinned for review, immutable evidence and history. Atomically compare grant subject and revision in core; attribute to the actual authority, never infer identity from the session token or fall back to automation. Existing routes retain safeguards; never extend gate kinds from UI. |
| Import and attach | No universal Studio route | Proposed `POST /assets/import` with bounded stream, allowlisted media probing, local staging and rights fields; response artifact ID/hash/availability. Never accept arbitrary server paths or URL fetching from Studio. Attachment uses asset IDs; approval coverage requires PF-22. |
| Batch/campaign | `POST /queue` only enqueues one saved job | Proposed `POST /batches` (explicit collection of stable row IDs), `POST /batches/:id/validate`, `/submit`, `GET /batches/:id`; campaign defaults revision and rebase preview then explicit conditional commit. No partial write at validation. |
| Export | `GET/POST /jobs/:id/export` | Proposed `POST /exports/plans` with job revisions and preflight, `POST /exports` with plan ID/action keys. No overwrite default; check each again; result receipt with independent statuses. |
| Activity | Stage and queue logs and handoffs | No general agent launcher. Read-only artifact and run receipts until a separate scope and permission contract exists. |

Candidate response semantics: `422` invalid input by field/row; `409` stale revision/key collision/lock; `202` accepted plus stable receipt URI; `200` read/replay; `404` unknown resource; `503` missing runtime prereq or unavailable snapshot with remediation. Keep the existing error envelope where compatible; client adapter maps status+code, not English text. Batch request `{revision, rows:[{rowId,specRevision}], intentKey}` follows the durable protocol below. `GET` must stay safe. Preserve local server origin/token protections; do not expose creds in receipts or actions via GET. Idempotency is proposed, not proven by the current UI lock.

## Sealed approval and attestation (proposed R3 contract)

- Give each sealed subject a versioned canonical encoding of workspace/job, gate, spec revision, subject revision and immutable reviewed evidence. Bind script/title for script review; bind the reviewed composition, dependency digests and relevant provenance for production. Serve previews from the same sealed bytes, not just a path that still exists. Pointer revision changes even if content bytes revert.
- The same core operation serves CLI and API. In one transaction, compare expected job/gate/revision/digest against the current sealed pointer and insert or replay the grant. All pointer changes and grant invalidations must serialize on that same boundary; a database lock does not freeze files. Reject malformed/missing confirmation, unavailable sealed subject and stale confirmation with no new grant. A duplicate action key with identical intent returns the same receipt; different intent conflicts. A historical receipt is never proof of current authorization.
- Keep old NULL/empty digest rows as audit history, never qualify them for a sealed gate or synthesize a digest for them. Fresh review is required; current export already rejects these rows, although pipeline stage gates can warn and pass. Replace or revoke with an auditable transition to at most one active grant per job/gate; fenced reruns that change the subject cannot resurrect a grant. Render evidence records sealed subject revisions, relevant grant IDs and exact output digest. Export rechecks eligibility and current grants at commit; changed inputs require the relevant fresh grant and rerender, not a relabel of old media.
- Attribute local sessions as `creator-studio-local` (server-assigned channel/session label), not username or authenticated principal. Keep an optional authenticated principal field populated only from a trusted identity layer, never client JSON. Existing PF-02 policy asks for authenticated human attribution; owner must clarify the live rollout bar. Separate authenticated private automation has explicit job/gate scope and content binding, not the Studio token or failed-human fallback.
- Acceptance: duplicate/replayed grant; absent/legacy/malformed digest; another job/gate; edit and revert; concurrent subject change and approve; rerun/invalidation racing grant; revoked or superseded grant with otherwise valid render; output substitution at export. Verify core and both clients; do not advertise exact-subject approval beforehand.

## Independent batch admission (proposed R4 contract)

1. Persist stable rows in `DRAFT`; validation sets batch `VALIDATING`, rows `READY` or `BLOCKED`, and stores each effective spec revision, validator/registry revision, and time-stamped capability evidence. The initial slice has no campaign inheritance. Recheck current availability at submission and again before execution; drift blocks only affected rows, keeps exact spec and requires fresh validation instead of substituting a renderer/voice/look.
2. Scope intent key to `(workspace, batch, operation, key)` and fingerprint a versioned canonical payload of batch revision and selected row IDs/spec revisions (sort by row ID where order is not semantic). Before filesystem effects, transactionally persist `SUBMITTING` plus row intents with reserved content IDs, spec hashes and stable submission keys. Same key and payload returns the original receipt even after jobs complete; same key with other payload conflicts. A separate key cannot enqueue an already submitted row revision again.
3. Materialize the spec atomically without overwriting different bytes; confirm durable file and containing directory before queue commit. In a single SQLite transaction, insert or link a queue entry with unique submission key and set row `SUBMITTED` with identifiers. It counts as submitted only after durable spec and queue intent. Aggregate `SUBMITTED` means every selected row accepted; `PARTIAL` lists mixed outcomes. Interrupted intents remain discoverable; validation blockers and integrity conflicts have distinct remediation.
4. A startup/explicit reconciliation command resumes pending intents, checks canonical file identity and queue key, and advances only the missing step. If a file matches and no queue row exists, revalidate then enqueue; if it differs, mark `NEEDS_REPAIR`; never mutate a foreign job. If an accepted spec later disappears, flag the accepted row and block its execution, not enqueue another. Repair or retry only unaccepted rows after review. Test process termination before and after file publication and directory fsync, between queue insert and row-state update (both in one transaction), after transaction commit, and during receipt readback/delivery. Reconcile and retry from a new process; require stable receipts, no duplicate jobs and no `SUBMITTED` status before durable spec and queue intent.

## Managed asset import (proposed, not R0/R1)

- Candidate first-release limits, to ratify after measurement: one import at a time, 250 MiB per file, 5 GiB managed quota including staging reservations, minimum 2 GiB disk headroom, 60 s no-progress timeout. Count actual bytes independent of header; release reservations on abort. Proposed first profiles (owner decision D3): PNG/JPEG up to 24 MP and WAV PCM up to two channels/48 kHz and 10 min. Defer video import until enforcement is demonstrated; MP4 H.264/AAC up to 1080p/60 fps and 10 min remains a later candidate, not an approved limit. Existing review of named local video artifacts is not managed import. Extension is a hint: require content probe and allowlisted declared streams, dimensions, duration and codec; reject unknown bounds, playlists and embedded attachments.
- Stream bytes from browser file picker to a private managed staging root; never accept original absolute paths or URLs. Exclusive generated filenames, directory-relative no-follow opens and regular-file checks; original name is display-only. Use a limited, offline probe child (10 s wall time, bounded output and 512 MiB memory target; kill process group on timeout; verify enforcement on target Mac before enabling). No transcode on import. Decode for previews only within separately enforced budgets; if effective wall-time, memory and isolation enforcement cannot be demonstrated on the target Mac, keep the importer disabled and offer the existing manual workflow as a handoff, not an alternate ingestion path.
- Hash while copying, verify before atomic promotion, dedupe content by digest but preserve each source/rights assertion. No live reference to the original, so a moved original is harmless. Cancel/disconnect releases owned temp and quota; startup reconciles only importer-owned partials, never user media. Same stored hash must be checked when attaching/sealing; missing or corrupt bytes block use without substitution. Store source display name, acquisition context and `unknown`, `operator_asserted`, or evidence-backed rights status, not a fabricated verified license.

**Assumptions:** compatibility remains the default, no schema deployment this phase. **Open questions:** owner asset families and attribution policy; measure import budget enforcement and choose durable receipt retention before rollout.
